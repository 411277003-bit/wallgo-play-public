## 3. 封包分析（簡報「分析：封包傳送之穩定度」）

指令：`python tests/packet_report.py --games 10 --remote https://wallgo-play.onrender.com`
方法：本機開真的後端，兩個機器人玩家透過 WebSocket 實際下完 10 局（1,002 個動作，全部被接受，花 58 秒）。

### 3-1 封包大小

| 封包 | 方向 | 平均 | 最大 | 說明 |
|---|---|---:|---:|---|
| `game_action`（我下了一步） | 玩家 → 伺服器 | 646 B | 857 B | 每次送整盤狀態 |
| 伺服器確認（ack） | 伺服器 → 玩家 | 15 B | 16 B | 只回版本號，例如 `{"version":12}` |
| `update_board`（對手下了一步） | 伺服器 → 其他人 | 789 B | 1,848 B | 多帶了領地資訊 |
| `sync_time`（倒數計時） | 伺服器 → 全房 | 36 B | 36 B | 每秒一次 |

封包會隨牆的數量變大（牆越多，盤面資料越多）：

| 場上牆數 | 0～9 道 | 10～19 道 | 20～29 道 |
|---|---:|---:|---:|
| 送出封包平均大小 | 595 B | 735 B | 829 B |

**報告時可以說：**「每一步不到 1 KB，一整局下來大約 100 KB。就算用手機網路也沒有負擔。」

### 3-2 延遲與穩定度（本機，沒有網路延遲，量的是伺服器處理時間）

| 指標 | 平均 | 中位數 | p95 | 最大 | 標準差 |
|---|---:|---:|---:|---:|---:|
| 送出到收到確認（含伺服器驗證棋步） | 6.2 ms | 6.1 ms | 9.1 ms | 15.3 ms | 1.8 ms |
| 送出到「對手畫面更新」 | 6.5 ms | 6.4 ms | 9.5 ms | 16.2 ms | 1.9 ms |
| 計時同步間隔（應為 1000 ms） | 1008.2 ms | 1007.3 ms | 1017.0 ms | 1019.0 ms | 5.1 ms |
| 斷線後重新入房並拿到盤面（10 次） | 13.1 ms | 12.4 ms | 29.4 ms | 29.4 ms | 6.1 ms |

- 計時同步 29 次之中，間隔超過 1.5 秒（等於掉了一拍）的有 **0 次**。
- 斷線重連 10 次，盤面**10 次都跟伺服器一致**。
- p95 的意思是「95% 的封包都比這個快」。

### 3-3 實際網路：台灣 → Render 雲端

| 指標 | 中位數 | 平均 | p95 | 最快 | 最慢 |
|---|---:|---:|---:|---:|---:|
| WebSocket 往返（30 次，不查資料庫） | **211 ms** | 234 ms | 396 ms | 164 ms | 411 ms |
| 建立 WebSocket 連線（5 次） | 926 ms | 909 ms | 1,045 ms | 756 ms | 1,045 ms |
| HTTP API（全站統計，含 TLS 與資料庫查詢，19 次） | 819 ms | 850 ms | 1,050 ms | 718 ms | 1,050 ms |
| **冷啟動**：伺服器閒置後的第一個請求 | **43.8 秒** | | | | |

**報告時可以說：**
- 「本機處理一步只要 6 ms，但真實網路往返大約 0.2 秒。可見延遲主要來自網路距離，不是程式本身。」
- 「Render 免費方案閒置 15 分鐘就會休眠，第一個人連進來要等 40 幾秒。這是免費方案的限制，改用付費方案或定時喚醒就能解決。」

### 3-4 作弊封包測試（伺服器的回應）

| 模擬的作弊 | 被接受？ | 伺服器回覆 | 回應時間 |
|---|---|---|---:|
| 憑空多放一顆棋 | ❌ | 資料格式錯誤：棋子資料不合法 | 3.7 ms |
| 把場上的牆全部拆掉 | ❌ | 不合法的操作 | 3.8 ms |
| 棋子瞬移 | ❌ | 不合法的操作 | 2.9 ms |
| 跳過自己的回合 | ❌ | 不合法的操作 | 3.2 ms |
| 破牆權用完又改回來 | ❌ | 不合法的操作 | 2.8 ms |
| 不是自己的回合卻送棋步 | ❌ | 還沒輪到你 | 3.6 ms |

每次拒絕時，伺服器還會附上正確的盤面（692 B），讓送出的人畫面自動恢復正確。

## 4. 壓力測試（簡報「分析：預計使用者數量」）

指令：`python tests/stress_test.py --rooms 10,50,100,200 --seconds 15`
方法：本機開真的後端，每間房 2 個機器人玩家真的在下棋，平均每 0.3 秒操作一次。每個等級跑 15 秒。

| 房間數 | 同時連線 | 15 秒處理動作 | 每秒處理 | 錯誤 | 確認延遲中位數 | p95 | p99 | 對手畫面更新 p95 | 伺服器記憶體 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 10 | 20 | 555 | 36 | 0 | 4.8 ms | 7.7 ms | 10.8 ms | 7.7 ms | 62 MB |
| 50 | 100 | 2,760 | 179 | 0 | 3.4 ms | 8.4 ms | 23.5 ms | 8.3 ms | 69 MB |
| 100 | 200 | 5,424 | 352 | 0 | 3.1 ms | 10.6 ms | 35.8 ms | 10.4 ms | 78 MB |
| **200** | **400** | 10,451 | **677** | 0 | **9.3 ms** | 107.8 ms | 164.9 ms | 120.1 ms | 96 MB |
| 300 | 600 | 6,291 | 405 ⚠️ | 0 | 192.3 ms | 461.8 ms | 649.1 ms | 463.5 ms | 107 MB |
| 400 | 800 | 5,211 | 333 ⚠️ | 0 | 351.5 ms | 772.9 ms | 1,017.6 ms | 792.4 ms | 130 MB |

**怎麼解讀：**
- **200 間房（400 人）以內**：每秒處理量隨房間數等比例增加，延遲中位數都在 10 ms 以下，伺服器處理得過來。
- **300 間房開始飽和**：每秒處理量不升反降，延遲跳到 200 ms 以上。所以**臨界點落在 200～300 間房之間**。
- 每一個等級都是 **0 個錯誤、0 個逾時**，也沒有任何合法棋步被誤擋。
- 記憶體大約每多 100 人增加 10～15 MB，400 人時約 96 MB。

**要誠實說明的限制：**
1. 機器人每 0.3 秒就操作一次，真人大約 1～2 秒才點一下，所以真人的負載大約只有機器人的 1/3～1/6。這是**偏嚴格**的測試。
2. 800 個機器人連線也跑在同一台電腦上，會跟伺服器搶 CPU。300 間房以上的數字可能有一部分是被客戶端拖慢的。
3. 這是在筆電上量的。Render 免費方案只有 0.1 顆 CPU、512 MB 記憶體，雲端上的上限會低很多。

**另外兩個量測：**
- **房號撞號**：300 個人同時要求房號 1234 → 分到 **300 間不同的房間**，只有第 1 個人拿到 1234，沒有人被踢掉。
  （修正前用 4 位數隨機房號，同時有 100 間房時至少撞號一次的機率約 42%，200 間約 89%。）
- **逾時代打的 AI 運算時間**：2 人局平均 0.7 ms（最慢 1.4 ms），4 人局平均 1.5 ms（最慢 3.7 ms）。後端是單執行緒，這段算越久所有房間越卡，實測影響可以忽略。

## 5. 測試過程中發現並修好的 bug（簡報「成品與產出流程」）

| # | 怎麼發現的 | 問題 | 影響 |
|---|---|---|---|
| 1 | 前後端一致性測試（讓真正的前端亂點） | 棋子停在四周牆位都滿的地方（例如角落），會卡在「建牆」階段沒東西可點 | 該玩家要等 90 秒逾時才能繼續；現在會直接換人 |
| 2 | 封包測試量不到計時封包 | 電腦同時裝了 eventlet 和 gevent 時，Flask-SocketIO 會自動選 eventlet，倒數計時完全不會執行 | 本機沒有倒數、逾時不會代打；現在明確指定 gevent |
| 3 | 同上，修好後重跑壓力測試 | 選錯非同步模式時效能也差：同樣 200 間房，每秒處理 364 個動作 → 指定 gevent 後 **677 個**，延遲中位數 220 ms → **9 ms** | 效能大約提升 1.9 倍 |
| 4 | 壓力測試的伺服器啟動失敗 | Windows 中文主控台（cp950）印 emoji 會讓伺服器在啟動時直接當掉 | 已修正 |
| 5 | 邊界測試 | 註冊時暱稱空白會造成伺服器錯誤 500 | 已修正 |

**報告時可以說：**「測試不只是驗證功能，還幫我們找到人工試玩不容易發現的 bug。像第 1 個要剛好走到角落、而且兩道牆都被蓋了才會出現；第 2 個只在特定環境才會發生。」

## 6. 自己用瀏覽器量（遊戲內建的封包紀錄器）

1. 開一場連線對戰，在對局頁網址後面加上 `&netlog=1`，或按 **Ctrl + Shift + L**。
2. 右下角會出現「📡 封包紀錄器」，即時顯示往返時間、封包大小、計時間隔、斷線重連時間。
3. 下完一局後按「下載 CSV」，用 Excel 開就能畫圖。檔案開頭幾行是統計摘要，後面是每一筆紀錄。
4. 想測斷線：在 F12 → Network → 把 No throttling 改成 Offline 幾秒再改回來，紀錄器會記下斷線和重連花了多久。

自己量完可以填在這裡（建議兩台裝置：一台電腦、一台手機用 4G）：

| 情境 | 動作數 | 往返中位數 | 往返 p95 | 送出封包平均 | 計時間隔標準差 | 斷線重連 |
|---|---:|---:|---:|---:|---:|---:|
| 電腦（Wi-Fi） | | | | | | |
| 手機（4G） | | | | | | |
| Chrome 模擬 Slow 4G | | | | | | |
